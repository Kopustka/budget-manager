# Budget Manager

Финансовый Telegram Mini App: учёт денег перетаскиванием. Доход тянут в кошелёк —
деньги зачисляются; кошелёк тянут в категорию — списываются. Прямая трата дохода
запрещена матрицей, лимиты категорий контролируются, бот присылает уведомления.

Четыре раздела: **Главная** (матрица, последние операции, создание кошельков и
категорий), **История** (лента за период с фильтрами и итогами), **Аналитика**,
**Настройки** (профили, валюта, начало расчётного месяца, выгрузка операций).

Календарь живёт не на главной, а в шторке записи операции: дата нужна ровно в
момент ввода, а первый экран она занимала постоянно. Тап по категории расхода
открывает её собственную историю за период с переходом в отфильтрованную «Историю».

Живой адрес: <https://budgetbottelegram.duckdns.org> · бот: [@bugetmanagementbot](https://t.me/bugetmanagementbot)

## Стек и структура

Монорепо на npm workspaces (Node 22+, PostgreSQL 18, Redis 8).

```
packages/shared      общие типы, zod-схемы DTO, правила DnD-матрицы
apps/api             Fastify + TypeScript: REST, бот (grammY), воркеры
apps/web             Vite + React 19 + Tailwind 4: Mini App
```

**PostgreSQL — источник истины, Redis — производный быстрый слой.** Каждая операция
идёт одной PG-транзакцией; Redis-команды копятся и выполняются одним pipeline сразу
после коммита. Если PG откатился, кэш не трогается; если упал Redis — кэш
пересобирается из PG, поэтому расхождение самоисправляется.

Правила матрицы (`packages/shared/src/matrix.ts`) — единственный источник для фронта
и бэка: фронт не отправляет заведомо запрещённый жест, бэк не доверяет фронту.

## Запуск для разработки

```bash
npm install
npm run build --workspace packages/shared      # общий пакет собирается в JS

cp .env.example apps/api/.env                  # заполнить DATABASE_URL, REDIS_URL, токен бота
npm run migrate                                # применить миграции
npm run seed --workspace apps/api              # тестовый пользователь и категории

npm run dev:api                                # http://localhost:3000
npm run dev --workspace apps/web               # http://localhost:5173
```

На сервере порт 3000 уже занят прод-сервисом `budget-api`, поэтому дев-стенд
поднимают на соседнем порту, а цель прокси vite переопределяют:

```bash
API_PORT=3001 npm run dev:api
API_PROXY_TARGET=http://127.0.0.1:3001 npm run dev:web
```

Фронт вне Telegram требует подписанный `initData` — проверка подписи на бэке
остаётся строгой:

```bash
# --silent обязателен: иначе в файл попадёт баннер npm и initData не разберётся
npm run --silent dev-init-data --workspace apps/api > apps/web/.env.local   # живёт 24 часа
```

## Проверки

| Команда | Что покрывает |
|---|---|
| `npm run typecheck` | типы во всех воркспейсах |
| `npm run smoke --workspace apps/api` | DnD-ядро через HTTP: матрица, лимиты, сверка PG↔Redis, полный откат при ошибке |
| `npm run smoke:alerts --workspace apps/api` | триггеры уведомлений, дедупликация, доставка воркером, планировщик |
| `npm run smoke:bot --workspace apps/api` | команды бота (апдейты подаются в handleUpdate, Bot API не вызывается) |
| `npm run smoke:settings --workspace apps/api` | границы периода при сдвинутом дне начала месяца, пересчёт валюты, CSV-выгрузка (отправка застаблена) |
| `npm run smoke:profiles --workspace apps/api` | профили: изоляция данных, одинаковые имена категорий в разных профилях, переключение, каскадное удаление, запрет удаления последнего |
| `npm run smoke:forecast --workspace apps/api` | прогноз бюджета (окно темпа, вердикты), дни без трат и серии, подстановка цифр в вечерний отчёт |
| `npm run smoke:crud --workspace apps/api` | создание кошельков и категорий: дубликаты имён, потолки, попадание новой категории в матрицу и аналитику |
| `npm run smoke:limits --workspace apps/api` | планирование расходов: upsert лимита, пороги SAFE/WARNING/EXCEEDED, атомарная проверка при списании, дедупликация пушей, снятие лимита |
| `npm run e2e --workspace apps/web` | сквозной DnD-сценарий в headless-браузере; `BASE_URL=https://…` прогоняет против прода |
| `npm run e2e:tabs --workspace apps/web` | четыре вкладки, фильтры и итоги «Истории», смена дня начала месяца |

`smoke:alerts`, `smoke:settings`, `smoke:limits`, `smoke:profiles` и `smoke:forecast` работают в отдельном namespace Redis
(`REDIS_NAMESPACE`), иначе запущенный воркер разбирает очередь у теста.

Браузерные прогоны создают кошельки и категории с префиксом `e2e ` и удалить их
через интерфейс нельзя — за собой они не убирают. Мусор подчищает `smoke:crud`
(он сносит и `smoke-crud %`, и `e2e %` у тестового пользователя), так что после
серии e2e стоит прогнать его, иначе упрётесь в потолок кошельков.

## Развёртывание

Собрать и разложить статику:

```bash
npm run build                                  # shared → api → web
cp -r apps/web/dist/* /var/www/budget-manager/
systemctl restart budget-api budget-bot budget-worker
```

Три systemd-юнита (`/etc/systemd/system/budget-*.service`):

| Юнит | Процесс |
|---|---|
| `budget-api` | REST API на :3000 (nginx проксирует `/api`) |
| `budget-bot` | long polling бота: `/start`, кнопка входа в Mini App |
| `budget-worker` | доставка уведомлений и планировщик напоминаний |

Бот и воркер разнесены намеренно: два процесса не могут делить один `getUpdates`.

nginx (`/etc/nginx/sites-available/budgetbottelegram.duckdns.org`) отдаёт статику и
проксирует `/api` на :3000 — один origin, поэтому CORS не нужен. Сертификат
Let's Encrypt продлевается таймером certbot.

Логи: `journalctl -u budget-api -f` (аналогично для `budget-bot`, `budget-worker`).

## Профили

Профиль — независимый бюджет: свои кошельки, категории, операции, лимиты, валюта
и день начала месяца. Общий у них только Telegram-аккаунт.

```
users                       ← кто ты в Telegram
  telegram_id, active_profile_id
     ├── profiles «Личный»    RUB, с 1 числа
     │      └── wallets · categories · transactions · limits · conversions
     └── profiles «Бизнес»    USD, с 10 числа
            └── wallets · categories · transactions · limits · conversions
```

Областью видимости данных до профилей был сам пользователь, поэтому миграция
`0005_profiles.sql` не надстроила уровень сбоку, а перенесла существующую связь
`user_id → profile_id` один к одному. Уникальность имён кошельков и категорий
теперь тоже внутри профиля: иначе «Кафе» нельзя было бы завести во втором.

Обработчики спрашивают `requireProfile(req)`, а не пользователя: активный профиль
подставляет auth-хук, и запрос всегда работает ровно с одной областью. Ключи
Redis — `finapp:profile:{profileId}:*`.

Уведомления приходят только по активному профилю: три профиля иначе давали бы три
вечерних напоминания, и их перестали бы читать. Удаление профиля уносит его данные
каскадом; последний удалить нельзя — приложению нечего будет открыть.

## Расчётный период и валюта

День начала месяца (`profiles.month_start_day`, 1–28) задаёт границы периода: метка
`YYYY-MM` означает отрезок, который **начинается** `YYYY-MM-<день>` и заканчивается
тем же числом следующего месяца. Например, при дне 2 период `2026-07` — со 2 июля по
1 августа включительно. Потолок 28 — чтобы период существовал и в феврале.

Формат ключей Redis и схема `category_limits` от этого не меняются, меняется только
смысл границ; при дне 1 поведение полностью совпадает с календарным месяцем.
Смена дня делает накопленные `spent` в Redis неверными, поэтому кэш профиля
чистится и пересобирается из PostgreSQL.

Доступные валюты (`packages/shared/src/currency.ts`): RUB, BYN, USD, EUR, KZT, GEL,
TRY, AMD. Смена валюты **пересчитывает** все суммы по курсу, введённому вручную (балансы,
операции, лимиты — одной PG-транзакцией). Операция необратима из приложения, каждый
прогон фиксируется в `currency_conversions`. Перед пересчётом стоит снять дамп.

Выгрузка операций приходит CSV-файлом в чат с ботом, а не скачиванием: в Telegram
WebView скачивание часто блокируется. Файл с BOM — чтобы Excel не ломал кириллицу.

## Планирование расходов и лимиты

Категории расхода несут запланированный бюджет на период — строка в
`category_limits` (`UNIQUE (category_id, period)`, сохранение идёт `INSERT … ON
CONFLICT DO UPDATE`). Задать и снять лимит можно при создании категории и в
шторке её правки (`PATCH /api/categories/:id`); `limitAmount: null` снимает план,
отсутствие поля — не трогает.

Статус категории нигде не хранится, а считается из плана и факта общей для фронта
и бэка функцией `limitStatus` (`packages/shared/src/limits.ts`):

| Статус | Доля лимита | Как выглядит |
|---|---|---|
| `SAFE` | < 85% | обычная стеклянная карточка |
| `WARNING` | 85–99% | тёплое оранжевое свечение |
| `EXCEEDED` | ≥ 100% | красный фон и граница `#FF3B30` |

Поэтому после Drag-and-Drop достаточно обновить одно число (`spent`) — карточка
перекрашивается сама, разъехаться посчитанному на лету статусу негде.

Проверка лимита при списании — **один `EVAL`** (`apps/api/src/redis/scripts.ts`):
записать `spent`, прочитать лимит, сравнить, поставить дедупликатор и положить
пуш в `finapp:queue:bot_alerts`. Порознь эти шаги оставляют окно, в которое
влезает параллельная трата по той же категории: превышение либо остаётся
незамеченным, либо порождает два уведомления. В `spent` пишется точное значение,
посчитанное `SUM`'ом в PostgreSQL после коммита, а не инкремент, — источник
истины остаётся один, и кэш не накапливает ошибку.

## Уведомления

Очередь на Redis: мгновенные пуши — LIST (воркер спит на `BRPOP`), отложенные — ZSET
по времени отправки. Триггеры:

- **лимит исчерпан** и **перерасход** — один раз на категорию за период;
- **слишком быстрые траты** — дневная трата вдвое выше нормы **и** накопленный факт
  обогнал план (одного дневного всплеска мало: кто неделю не тратил, тот в графике);
- **«День в цифрах»** — вечерний отчёт: потрачено за день, уложились ли в лимиты,
  остаток бюджета на месяц. В день без трат вместо цифр — поздравление и текущая серия.

Дедупликация — через `SET NX EX`, поэтому повторные операции не порождают спам.

Отчёт кладётся в очередь **без цифр**: планировщик ставит его сильно раньше времени
отправки, и посчитанные тогда суммы к вечеру устарели бы. Числа подставляет
`hydrateAlert` в момент доставки.

## Прогноз и дни без трат

`GET /api/analytics/forecast` — на сколько хватит бюджета при нынешнем темпе.
Средний расход считается по **последним полным дням, заканчивая вчерашним**:
сегодняшний неполный и занижал бы темп тем сильнее, чем раньше открыто приложение.
У новых профилей окно короче недели — сколько дней реально попало в расчёт, видно
в интерфейсе, иначе «среднее за неделю» по двум дням вводило бы в заблуждение.
База — сумма лимитов периода; без лимитов прогноза не существует, и интерфейс
говорит об этом прямо, а не подставляет правдоподобное число.

`GET /api/analytics/no-spend` — дни периода без единого расхода, текущая и лучшая
серии. Зачисление дохода день не портит. Серия считается **от даты первой операции**:
иначе новый профиль получал бы серию за дни, когда приложением не пользовались.

## Что стоит доделать

- Сервисы работают от `root`, потому что проект лежит в `/root`. Для боевой
  эксплуатации — вынести код в `/srv` и завести отдельного пользователя.
- Токен бота светился в переписке: перевыпустить через BotFather и обновить
  `apps/api/.env`.
- Резервное копирование PostgreSQL не настроено: дампы снимаются руками в
  `/root/backups` (`pg_dump "$DATABASE_URL" -Fc -f …`).
- Категории можно создавать и править (название, оформление, месячный лимит), а
  кошельки — только создавать. Удаления нет ни у тех, ни у других: у него
  неочевидная семантика (что делать с уже записанными операциями), и решать её
  нужно отдельно. У профилей удаление есть — там семантика однозначна: уходит
  весь бюджет целиком.
- Профиль принадлежит одному Telegram-аккаунту. Совместный доступ (семейный
  бюджет) потребует таблицы участников вместо `profiles.user_id` — это отдельная
  миграция, данные при ней не переезжают.
